# Langfuse ClickHouse → BigQuery Pipeline

Incrementally loads **traces** and **scores** from Langfuse's internal ClickHouse database into BigQuery using [dlt](https://dlthub.com).

---

## How it works

The pipeline connects directly to Langfuse's ClickHouse database over HTTP and reads the `traces` and `scores` tables. On the first run it loads all records from the `start_date` defined in `params.yaml`. On every subsequent run it only fetches rows where `updated_at` is newer than the last run — no full table scans.

| Table | Incremental cursor | Primary key | Write mode |
|---|---|---|---|
| `traces` | `updated_at` | `(id, project_id)` | merge (upsert) |
| `scores` | `updated_at` | `(id, project_id)` | merge (upsert) |

ClickHouse's `ReplacingMergeTree` duplicates are collapsed using `FINAL` before reading. Map and Array columns (`metadata`, `input`, `output`, `tags`) are cast to JSON strings in SQL so they land as single columns in BigQuery rather than being flattened.

## Environment setup

The pipeline uses `params.yaml` to switch between `dev` and `prod` environments. The environment is determined automatically from the current git branch:

| Branch | Environment | BigQuery dataset |
|---|---|---|
| `main` | `prod` | `langfuse_clickhouse` |
| any other | `dev` | `langfuse_clickhouse_dev` |

To override manually:
```bash
ENV=prod python langfuse_pipeline.py
```

## Setup

### 1. Install dependencies

Requires [uv](https://docs.astral.sh/uv/). Install it if needed:
```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

Then install dependencies from the lockfile:
```bash
uv sync
```

### 2. Configure `.dlt/config.toml`

```toml
[sources.langfuse_clickhouse_source]
host       = "your-clickhouse-host"
port       = 8123
database   = "default"
```

### 3. Configure `.dlt/secrets.toml`

```toml
[sources.langfuse_clickhouse_source]
username = "default"
password = "your-clickhouse-password"

[destination.bigquery.credentials]
project_id   = "your-gcp-project-id"
client_email = "your-service-account@your-gcp-project-id.iam.gserviceaccount.com"
private_key  = "-----BEGIN RSA PRIVATE KEY-----\n...\n-----END RSA PRIVATE KEY-----\n"
```

> `secrets.toml` is gitignored and must never be committed. Share credentials with teammates via a password manager or GCP Secret Manager.
>
> Alternatively, set `GOOGLE_APPLICATION_CREDENTIALS=/path/to/sa-key.json` instead of inlining the BigQuery credentials.

### 4. Run

```bash
uv run python langfuse_pipeline.py
```

## BigQuery output

After the first successful run, two tables are created in the target dataset:

- `traces` — one row per Langfuse trace
- `scores` — one row per evaluation score

A `langfuse_clickhouse_dev_staging` / `langfuse_clickhouse_staging` dataset is also created automatically by dlt as a temporary landing zone during the merge — this is expected and can be ignored.

## GitHub Actions

The pipeline runs automatically via `.github/workflows/pipeline.yml`.

### Triggers

| Trigger | Branch | Environment | Dataset |
|---|---|---|---|
| Push | `main` | prod | `langfuse_clickhouse` |
| Push | `development` | dev | `langfuse_clickhouse_dev` |
| Schedule (daily 8.30pm UTC) | `main` | prod | `langfuse_clickhouse` |
| Manual (`workflow_dispatch`) | any | detected from branch | — |

### Workflow steps

```
1. Checkout repository
      ↓
2. Install uv
      ↓
3. Install dependencies (uv sync — uses uv.lock for reproducible installs)
      ↓
4. Write .dlt/secrets.toml from GitHub Secrets
   (.dlt/config.toml is committed to the repo and used as-is)
      ↓
5. Run pipeline (uv run python langfuse_pipeline.py)
   GITHUB_REF_NAME is set automatically by GitHub Actions to the branch name.
   utils.get_params() reads it to select dev vs prod environment.
      ↓
6. Upload dlt pipeline state as artifact (runs even if pipeline fails,
   so the incremental cursor is preserved for inspection after each run)
```

### Required GitHub Secrets

Add these under **org/repo → Settings → Secrets and variables → Actions → Secrets**:

| Secret | Value |
|---|---|
| `CLICKHOUSE_USERNAME` | ClickHouse username |
| `CLICKHOUSE_PASSWORD` | ClickHouse password |
| `BIGQUERY_PROJECT_ID` | GCP project id |
| `BIGQUERY_CLIENT_EMAIL` | Service account email |
| `BIGQUERY_PRIVATE_KEY` | Full private key including `-----BEGIN...END-----` |

> `config.toml` is committed to the repo so it does not need to be recreated in CI. Only `secrets.toml` is written by the workflow since it is gitignored.

### Pipeline state in CI

GitHub Actions runners are ephemeral — the `.dlt/pipelines/` directory is lost after every run. The workflow uploads it as an artifact (retained for 7 days) so you can inspect the cursor state after a run. However, state is **not automatically restored** between runs, meaning each CI run currently starts from `start_date` in `params.yaml`.

if: always() in the pipeline makes sure that artifact upload step still runs even if the pipeline crashes midway. This makes sure that if the pipeline fails halfway through, incremental cursor state dlt managed to write before the failure is saved.

To persist the incremental cursor across CI runs properly, store the dlt state in BigQuery by calling `pipeline.sync_destination()` after a successful run — this is recommended once the pipeline is stable in production.

## Resetting the pipeline

To force a full reload from `start_date` (e.g. after changing columns or the start date):

```bash
rm -rf .dlt/pipelines/
uv run python langfuse_pipeline.py
```

## Adding a new table

1. Add the table and its columns to `schemas/import/langfuse_clickhouse_source.schema.yaml`
2. If the table has Map or Array columns, add them to `cast_columns` in `langfuse_pipeline.py`
3. Run the pipeline — the new table is picked up automatically
